# Задание 3. Стратегия защиты данных: Encryption at Rest and In Transit

## Вывод

Стратегия: шифрование всех данных классов C2–C3 в обоих состояниях (at rest и in transit) с централизованным управлением ключами (Vault/KMS); для состояния in use — контроль доступа (RBAC/ABAC), маскирование и псевдонимизация. Выбор инструмента определяется классом чувствительности и профилем риска, а не системой-хранителем: политика привязана к тегам данных (см. Task 1) и применяется одинаково в любом хранилище и канале.

## 1. Классификация данных

### 1.1. По чувствительности

| Класс | Состав | Правовое основание защиты |
|---|---|---|
| **C3 — врачебная тайна и специальные категории ПДн** | ЭМК, диагнозы, заключения, результаты анализов, анкеты о хронических заболеваниях, таблица соответствия surrogate ID | 323-ФЗ ст. 13; 152-ФЗ ст. 10; приказ ФСТЭК № 21 |
| **C2 — ПДн и финансовые данные** | Ф. И. О., дата рождения, контакты, паспортные данные, СНИЛС/ИНН, договоры, платежи, зарплаты и кадровые данные сотрудников | 152-ФЗ; НК РФ, ТК РФ; 54-ФЗ (фискальные данные) |
| **C1 — внутренние данные** | Учёт ТМЦ, закупки, расписания без привязки к пациентам, внутренние регламенты | Коммерческий интерес компании |
| **C0 — публичные** | Прайс-лист, список услуг, контакты клиники | Не требуют защиты, требуют контроля целостности |

### 1.2. По состоянию

| Состояние | Где возникает | Базовый метод защиты |
|---|---|---|
| **At rest** — хранение | Postgres, MinIO/S3 (сканы), ClickHouse, базы 1С, резервные копии, таблица псевдонимов | Шифрование: TDE/pgcrypto, SSE-KMS, шифрование бэкапов; ключи в Vault |
| **In transit** — передача | Браузер/приложение ↔ порталы; сервис ↔ сервис; ККМ ↔ платёжный сервис; обмен с лабораторией, банком, ФНС; репликация и бэкапы между площадками | TLS 1.3 (минимум 1.2 для legacy), mTLS для сервисов, ГОСТ TLS для госорганов, VPN между филиалами |
| **In use** — обработка | Интерфейсы сотрудников, BI, ML-обучение | Шифрование неприменимо: RBAC/ABAC, маскирование в UI, псевдонимизация для аналитики, аудит обращений |

### 1.3. По профилю риска

| Угроза | Целевые данные | Компенсирующий контроль |
|---|---|---|
| Инсайдер (растущий штат новых сотрудников) | C3, C2 в интерфейсах и выгрузках | ABAC «лечащий врач», маскирование, DLP, аудит + поведенческие алерты |
| Перехват в сети (в т. ч. legacy-канал ККМ) | Платёжные данные, ПДн в интеграциях | mTLS, отказ от OLE, сегментация сети |
| Кража носителей / физический доступ к серверу в офисе | Все данные at rest | Полнодисковое + прикладное шифрование, ключи вне сервера (Vault/HSM) |
| Компрометация внешнего контрагента (лаборатория) | Направления и результаты анализов | Псевдонимизация (surrogate ID), контракт API без ПДн |
| Потеря/кража резервных копий | Полные срезы всех БД | Обязательное шифрование бэкапов, ключи отдельно от носителя |
| Программы-вымогатели | Доступность всех данных | Иммутабельные (WORM) копии, офлайн-копия вне офиса |

## 2. Таблица: данные — необходимость защиты — инструменты

| Данные | В чём необходимость защиты | Инструменты защиты |
|---|---|---|
| ЭМК: диагнозы, заключения, назначения (C3) | Врачебная тайна (323-ФЗ ст. 13); утечка — оборотные штрафы (КоАП 13.11), потеря доверия клиентов | At rest: pgcrypto/TDE в Postgres, ключи в Vault. In transit: TLS 1.3, mTLS между сервисами. In use: ABAC «мед. допуск + лечащий врач», аудит каждого чтения в SIEM |
| Сканы медицинских документов и результаты анализов (C3) | Та же категория тайны; сейчас лежат на общем диске без контроля | MinIO с SSE-KMS (ключи Vault через KES), presigned-ссылки с TTL, доступ через API с проверкой прав, DLP на периметре |
| Таблица соответствия surrogate ID ↔ пациент (C3) | Компрометация раскрывает все псевдонимизированные данные разом | Отдельная БД сервиса псевдонимизации, pgcrypto, доступ только сервисному аккаунту, аудит каждого resolve, ключи в Vault |
| Ф. И. О., дата рождения, контакты пациентов (C2) | ПДн (152-ФЗ); основа фишинга и социнженерии против клиентов | At rest: шифрование на уровне СУБД. In transit: TLS. In use: маскирование телефона/e-mail в интерфейсах ролей, которым полное значение не нужно |
| Паспортные данные, СНИЛС в договорах (C2) | ПДн повышенного риска: мошенничество, кредиты на чужое имя | Поле-уровневое шифрование (pgcrypto), частичное маскирование в UI, доступ только роли, оформляющей договор |
| Платёжные и фискальные данные (C2) | 54-ФЗ, банковская тайна; подмена данных чека — финансовые потери | Замена OLE-канала ККМ на API с mTLS; TLS к платёжному шлюзу; карточные данные не хранятся (передаются шлюзу напрямую) |
| Кадровые данные и зарплаты сотрудников (C2) | ПДн работников; внутренние конфликты и утечки при компрометации | Перевод 1С в клиент-серверный режим, шифрование БД, доступ только ролям hr/accountant, ГОСТ-каналы к ФНС/СФР |
| Озеро данных для BI/ML (производное от C2/C3) | Вторичное использование без согласия допустимо только для обезличенных данных (152-ФЗ) | Обязательная псевдонимизация на входе (движок классификации), шифрование дисков ClickHouse, RBAC analyst, запрет resolve из контура аналитики |
| Резервные копии всех хранилищ | Одна украденная лента/диск = утечка всех данных сразу | Шифрование бэкапов (AES-256), ключи в Vault отдельно от носителей, иммутабельные копии, офсайт-хранение, регулярное тестовое восстановление |
| Журналы аудита и логи | Доказательная база для расследований; в логи могут попадать ПДн | Иммутабельное хранение (WORM-индексы Elastic), запрет записи ПДн в логи (маскирование на уровне логгера), TLS при отправке |
| Секреты приложений: пароли БД, API-ключи, сертификаты | Компрометация секрета = обход всей защиты данных | Vault (KV + PKI), динамические учётные данные, ротация, запрет секретов в коде и конфигах (CI-сканер) |
| Данные ТМЦ и закупок (C1) | Коммерческая информация; целостность учёта | TLS in transit, разграничение доступа ролью warehouse; шифрование at rest — в составе общего шифрования дисков |

## 3. Автоматизированный контроль

| Контроль | Что проверяет | Инструмент |
|---|---|---|
| Сканер классификации | Непомеченные конфиденциальные данные в хранилищах (регулярный обход) | Движок классификации (Task 6) + каталог данных OpenMetadata |
| CI-проверка релизов | Миграции схем и API-контракты, затрагивающие теги c2/c3, без шифрования/маскирования — блокировка релиза | Пайплайн CI + правила по каталогу тегов |
| Контроль TLS-конфигураций | Версии протоколов, cipher suite, сроки сертификатов | cert-manager (автопродление), сканер конфигураций (testssl.sh в CI), алерты Victoria Metrics |
| Контроль ключей | Ротация, попытки несанкционированного доступа к Vault, использование ключей | Аудит-лог Vault → Elastic SIEM, алерты |
| Мониторинг обращений к данным | Нетипичные объёмы чтения c3, доступ вне рабочего времени, массовые выгрузки | Elastic SIEM (корреляционные правила) + Victoria Metrics (метрики) → алерты команде безопасности |
| DLP-контроль периметра | Передача тегированных c2/c3 данных через почту, USB, печать, веб | DLP-система, интеграция с тегами классификации |
| Контроль бэкапов | Факт шифрования, успешность копий, периодическое тестовое восстановление | Система резервного копирования + алерты; регламентные восстановления |
| Сканирование секретов | Секреты в коде, репозиториях, образах | Сканер секретов в CI (gitleaks) |

## Trade-offs

- **Поле-уровневое шифрование (pgcrypto) против TDE**: pgcrypto защищает даже от администратора СУБД, но ломает индексирование зашифрованных полей и усложняет запросы. Применяется точечно (паспортные данные, таблица псевдонимов); для остального достаточно шифрования тома + контроля доступа.
- **ГОСТ-контур**: обязателен для обмена с госорганами, но требует сертифицированных СКЗИ и их сопровождения — выделяется в отдельный шлюз, чтобы не тащить КриптоПро во все сервисы.
- **HSM**: даёт максимальную защиту мастер-ключей, но дорог; на этапе MVP допустим Vault с auto-unseal и строгим контролем доступа, HSM — при масштабировании на филиалы.
