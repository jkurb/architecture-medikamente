# Данные для защиты, механизм тегирования и инструменты

## 1. Классы данных и способы защиты

Уровни конфиденциальности: **C3** — врачебная тайна и спец. категории ПДн, **C2** — ПДн и финансовые данные, **C1** — внутренние данные, **C0** — публичные.

| Данные | Уровень | Шифрование | Обфускация / маскирование | Обезличивание |
|---|---|---|---|---|
| Медкарты, заключения, диагнозы, хронические заболевания | C3 | At rest (TDE/pgcrypto) + in transit (TLS 1.2+); ключи в KMS | Маскирование в интерфейсах для ролей без мед. допуска | Псевдонимизация (пациент → surrogate ID) для аналитики и тестовых сред |
| Результаты анализов | C3 | At rest + in transit; шифрование файлового хранилища сканов | Скрытие в API-контрактах для внешних потребителей | Псевдонимизация при передаче в озеро данных |
| Расширенная анкета (адрес, место работы/учёбы) | C3 | At rest + in transit | Маскирование по умолчанию, раскрытие по отдельному праву | Не собирать без цели (Data Minimization); в аналитике — только агрегаты |
| Паспортные данные, СНИЛС, ИНН (пациенты и сотрудники) | C2 | At rest + in transit | Частичное маскирование (`4510 **** **`) везде, кроме кадров/договорного контура | Полное удаление из аналитических выгрузок |
| Ф. И. О., дата рождения, телефон, e-mail | C2 | In transit; at rest на уровне СУБД | Маскирование телефона/e-mail (`+7***1234`) в журналах и логах | Замена на surrogate ID в озере данных |
| Платёжные данные, суммы по договорам | C2 | In transit (ККМ ↔ учёт — по защищённому каналу вместо OLE), at rest | Скрытие реквизитов в отчётах | Агрегирование в BI-отчётах |
| Зарплаты, банковские реквизиты сотрудников | C2 | At rest + in transit | Доступ только роли «бухгалтерия», маскирование для остальных | — |
| Данные ТМЦ, закупки | C1 | In transit | — | — |
| Резервные копии всех C2/C3-хранилищ | наследует | Обязательное шифрование бэкапов, ключи отдельно от данных | — | — |

Правила выбора способа:
- **Шифрование** — базовая мера для хранения и передачи; не заменяет контроль доступа.
- **Маскирование/обфускация** — для отображения данных ролям, которым полное значение не нужно для работы.
- **Обезличивание/псевдонимизация** — обязательно для вторичного использования: аналитика, BI/ML, тестовые среды (152-ФЗ допускает обработку обезличенных данных без согласия).

## 2. Механизм тегирования данных

### Модель тегов

| Тег | Значения | Назначение |
|---|---|---|
| `confidentiality` | `c0/c1/c2/c3` | Уровень конфиденциальности, определяет меры защиты |
| `category` | `medical / pii / payment / hr / inventory` | Домен данных, определяет владельца и политику доступа |
| `retention` | срок хранения | Автоматическое удаление по истечении срока |
| `consent-scope` | цель обработки | Проверка соответствия обработки согласию субъекта |

### Применение тегов

1. **Уровень схемы данных.** Теги на колонках/таблицах Postgres (метки в каталоге данных, COMMENT-конвенция) и на объектах файлового/объектного хранилища.
2. **Каталог данных** (OpenMetadata / DataHub) — единый реестр: датасеты, теги, владельцы, lineage. Закрывает требование Data Lineage.
3. **Автоматическая классификация.** Движок классификации сканирует новые данные перед загрузкой в хранилище (regex + словари + ML-классификатор для Ф. И. О., телефонов, СНИЛС, диагнозов) и проставляет теги; спорные случаи — на ручную разметку. (Реализация движка — Task 6.)
4. **Принудительное применение (enforcement).** Политики доступа (RBAC/ABAC) ссылаются на теги, а не на конкретные таблицы: правило «роль без мед. допуска не читает `c3`» действует автоматически для любых новых данных — новые интеграции не требуют перевалидации (Privacy by Design).
5. **Контроль в релизном цикле.** CI-проверка: миграции схем и API-контракты, затрагивающие тегированные данные `c2/c3`, блокируются без маскирования/шифрования; результат передаётся в мониторинг и алертинг.

## 3. Инструменты и меры обеспечения конфиденциальности

| Слой | Мера | Инструменты (с учётом стека компании) |
|---|---|---|
| Идентификация и доступ | Централизованный IdP, SSO, MFA; RBAC/ABAC по тегам; least privilege | Keycloak (интеграция с существующим AD/LDAP) |
| Хранение | Перенос данных с общего диска в СУБД и объектное хранилище; шифрование at rest | PostgreSQL (pgcrypto/TDE), MinIO/S3 с SSE, ключи — HashiCorp Vault |
| Передача | TLS везде; отказ от OLE-канала ККМ в пользу защищённого API; шифрованная почта для внешних контрагентов | TLS 1.2+, mTLS между сервисами, API-шлюз |
| Аудит | Журналирование всех обращений к C2/C3-данным; выявление нетипичных действий; алертинг | Elastic (SIEM), Victoria Metrics + алерты; неизменяемые журналы аудита |
| Предотвращение утечек | DLP на периметре (почта, USB, печать), контроль общего диска на период миграции | DLP-система, запрет локальных выгрузок ПДн |
| Аналитика | Озеро данных только с псевдонимизированными данными; работа аналитика в контролируемой среде вместо локального Jupyter | ClickHouse (обезличенный слой), каталог данных с lineage |
| Каталог и lineage | Реестр датасетов, теги, происхождение данных | OpenMetadata / DataHub |
| Резервирование | Шифрованные бэкапы вне офиса, регулярное тестирование восстановления | Средства резервного копирования с шифрованием |
| Организационные | Реестр обработки ПДн, политика доступа, процесс запросов субъектов (удаление/отзыв согласия), обучение сотрудников, NDA | Регламенты; назначение ответственного за обработку ПДн |
